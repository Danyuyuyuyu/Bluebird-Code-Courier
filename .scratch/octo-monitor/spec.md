# OCTO 仓库监控器 · v1 Spec

**Status: ready-for-agent**

## Problem Statement

用户关注着一批 GitHub 开源仓库，想知道它们"有没有新东西"——出了新版本、最近在改什么、议题多不多、构建是否还健康。现状是只能挨个打开 GitHub 页面人肉翻，或者使用那两个只有界面没有数据链路的原型；既看不出"哪几个仓库有更新"，也无法回看指标随时间的变化。

## Solution

一个本地优先的桌面 App（Windows 先行）：把关注的仓库放进**监控清单**，打开即自动**抓取**每个**监控仓库**的**轻量信息**（star、**最近动态时间**、最新发版标签），一眼看出有没有**更新**；点开某个仓库看**全量信息**——发版、提交、议题与合并请求、构建状态四类内容与星标**趋势**；每次成功抓取按日留存**历史快照**，趋势随使用自然积累。**访问令牌**必填并存本机，数据全在本机，打开即用、关闭即停。

## User Stories

1. 作为一名仓库观察者，我希望首次启动时填写并验证我的**访问令牌**，以便立刻获得充足的抓取配额。
2. 作为一名仓库观察者，我希望令牌无效时得到明确提示并被带回设置页，以便不用猜哪里错了。
3. 作为一名仓库观察者，我希望把 owner/repo 加入**监控清单**，以便开始跟踪它。
4. 作为一名仓库观察者，我希望添加不存在或无权访问的仓库时立即收到明确报错，以便不把坏条目留在清单里。
5. 作为一名仓库观察者，我希望从**监控清单**删除某个**监控仓库**，以便清单里只剩我真正在意的。
6. 作为一名仓库观察者，我希望清单在关闭重开后依然存在，以便不用每次重新配置。
7. 作为一名仓库观察者，我希望清单里每个仓库直接显示**轻量信息**（star、最近动态时间、最新发版标签），以便一眼看出有没有**更新**。
8. 作为一名仓库观察者，我希望启动时自动抓取一次**轻量信息**，以便打开就能看。
9. 作为一名仓库观察者，我希望在清单页手动重新抓取**轻量信息**，以便马上看到当前状态。
10. 作为一名仓库观察者，我希望点开某个仓库看到**全量信息**，以便深入了解它的**更新**。
11. 作为一名仓库观察者，我希望**全量信息**按**更新类别**分区展示（发版 / 提交 / 议题与合并请求 / 构建状态 / 星标趋势），以便分类查看。
12. 作为一名仓库观察者，我希望看到发版列表（标签、标题、日期），以便知道它出了哪些版本。
13. 作为一名仓库观察者，我希望看到提交列表（消息、作者、时间），以便知道最近改了什么。
14. 作为一名仓库观察者，我希望议题与合并请求分开展示，以便区分两类工作。
15. 作为一名仓库观察者，我希望看到构建状态徽章，以便知道最近一次构建是否通过；没有构建的仓库显示"无构建"。
16. 作为一名仓库观察者，我希望看到星标与分叉的**趋势**，以便感知仓库的成长。
17. 作为一名仓库观察者，我希望在详情页手动重新抓取**全量信息**，以便看到此刻的最新内容。
18. 作为一名仓库观察者，我希望每次成功抓取都留下**历史快照**（每天一档），以便**趋势**随使用积累。
19. 作为一名仓库观察者，我希望手动刷新的抓取也记入**历史快照**，以便我主动关注的时刻被留存。
20. 作为一名仓库观察者，我希望某仓库没有发版时看到明确空态（"无发版"），以便不误判为出错。
21. 作为一名仓库观察者，我希望网络失败时看到上次数据加明确错误提示，以便知道只是暂时问题。
22. 作为一名仓库观察者，我希望被限流时的提示带上恢复时间，以便知道何时再试。
23. 作为一名仓库观察者，我希望令牌失效（401）时被明确告知并引导去设置页，以便换令牌后继续用。
24. 作为一名仓库观察者，我希望 App 双击即用、关闭即停、不留后台进程，以便对设备完全掌控。
25. 作为一名仓库观察者，我希望数据只存在本机，以便隐私不外流、断网也能翻看已有内容。
26. 作为一名小圈子成员，我希望能独立安装、各用各的令牌和清单，以便互不干扰。
27. 作为一名仓库观察者，我希望界面对小屏友好，以便手机端到来时交互一致。
28. 作为一名维护者，我希望两个平台的实现遵循本 spec 约定的同一套数据结构与规则，以便 Windows 与 Android 端行为一致。

## Implementation Decisions

**架构与模块**（模块化 + 基础设施）：Electron 双进程——主进程承载服务层（`core`：GitHub 抓取、本地数据库、令牌存取、日志；`features`：监控清单、抓取编排、历史快照、设置），渲染进程只做 UI（`features`：监控清单、清单页、详情页、历史快照、设置），preload 以白名单 IPC 暴露**用例门面**。feature 之间不直接引用；core 不依赖 feature。UI 组合已定：React 18 + TypeScript + Tailwind + TanStack Query + Chart.js。

**用例门面**（渲染层唯一入口）：清单的增删与列举（返回**轻量信息**）、单仓库**全量信息**抓取、按场景触发的重新抓取（清单页=轻量、详情页=全量）、访问令牌校验与保存、设置读写。

**数据表**（与 Android 端同语义）：

- `repository`：id、owner、name、full_name（唯一）、added_at，以及最近一次成功抓取的展示字段 stars、forks、open_issues、pushed_at、latest_release_tag、fetched_at（可空）
- `snapshot`：id、repository_id、captured_at、stars、forks、open_issues、latest_release_tag、pushed_at；唯一约束（repository_id + 本地日期）
- `setting`：key、value（访问令牌加密存放、偏好项）

**抓取与 API 调用清单**：轻量=每仓库两次调用（仓库元数据含 star/fork/open issues/最近推送时间 + 最新发版）；全量=发版列表、提交列表、议题与合并请求列表（同一端点返回、按是否带 pull_request 标记拆分）、构建状态（取最近一次构建结论，无则空态）；趋势不调接口、只读快照。请求带令牌与固定 API 版本号。

**快照规则**：仅成功抓取后记档；同一仓库同一天只留一档（本地日期）；手动刷新同样记档；缺省值（如无发版）记空。

**错误与降级**：错误归一为五类——令牌无效、限流、不存在/无权限、网络失败、未知；一律"显示上次数据 + 错误条"，限流提示带恢复时间。

**交互与窗口**：启动→轻量抓取→点开→全量抓取→按钮手动刷新；普通窗口，无托盘、无开机自启；时间存储 UTC ISO8601、展示相对时间。

**打包**：Windows NSIS 安装包（electron-builder）。

## Testing Decisions

- **好测试只测外部行为**：给定输入 → 断言用例门面的返回值与数据库落档；不测内部调用顺序、不测私有状态、不测 UI 组件结构。
- **唯一测试缝**：主进程用例门面。GitHub 侧以假适配器替换（fixtures 按实现决策中的抓取与 API 调用清单录制，含限流/401/404 场景），SQLite 用临时文件真库（顺带验证建表与迁移）。
- **被测模块**：监控清单持久化、轻量信息抓取、全量信息抓取、历史快照日档去重、错误归一与降级、令牌校验保存——全部经由用例门面覆盖。
- **Prior art**：无（本仓库首个测试套件）。用 Vitest 建立，后续模块测试一律向此看齐；UI 不写单测，由验收清单人工验收。

## Out of Scope

通知渠道；共享/多用户；事件留存与已读状态（本产品不做事件流）；云同步或真服务端；Android 端实现（v1.1 另立 spec，按本 spec 的数据结构与规则对齐）；监控模式（Watching/Starred 区分）；导出备份；原型中的 CI 流水线阶段动画、双轴大图表、Webhook 终端、AI 哨兵、模拟数据源与演示令牌、限流遥测仪表、告警铃铛。
